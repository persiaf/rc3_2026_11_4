# 冻结旧 MLP 与 Detour：400 ms 软预算补充结果

**当前机器上的描述性补充结果支持“冻结旧 MLP 可作为质量模式候选”：在接近的实际规划时间下，平均配对成本比 Detour 低 0.2880%，95% 场景 bootstrap 区间为 [0.0268%, 0.5818%]。** 该收益较小，测试仍只有原 18 个百桌场景，且本实验是在看到第四版结果后追加，不能替换原来的模型采用判断。

## 实际执行与边界

运行时间为 2026-11-03 03:42:23 至 03:43:23 UTC，18 个场景、2 种方法、各 3 次随机交错，共 **108 次**。正式循环及统计耗时 **59.98 s**。

- **108 / 108** 次返回方案通过原计时边界之外的额外独立验证。
- **108 / 108** 次与重新验证的原保存 Fixed3 方案成本界一致；运行时生成的参考成本也与该保存方案相同。
- 两种方法均没有触发回退。原源码、冻结模型与输入场景的运行前后哈希均未变化。
- 直接复用未修改的 `rc3_v4.evaluate.run_once`、`rc3_v4.runtime.run` 和 `LegacyMLPPolicy`。没有改动算法、软预算、修复上限、STOP 阈值或返回策略，没有训练或选择模型。
- 旧权重 SHA-256 为 `63e200f204b1e53c630f178bf7f60665944222becb60126b11c6461613db234d`。

平台：Linux 6.18.57、Python 3.12.14、NumPy 2.3.5、SciPy 1.17.0；CPU 报告为 Intel Xeon Platinum 8573C，容器 CPU 配额为 `800000 / 100000`。这是当前共享执行环境的结果，不是原 Windows 性能复测的等价硬件替代。正式运行期间已协调避免其他代理的重型测试，但没有将主机其他负载视为完全受控。

## 同一批 18 个百桌场景的结果

成本目标仍为 `J=导航路程+0.75×服务配置数量`，不能将成本下降直接解释为机器人任务完成时间同比下降。每场景三次成本取均值、规划时间取中位数，然后在场景层面汇总。

|场景数 / 运行数|18 / 54|18 / 54|

两种方法全部以 `deadline` 结束。400 ms 是开始新修复的软时间预算；已开始的原子修复和必须执行的最终验证可以超过截止时间，因此本结果不构成“400 ms 内返回”的保证。额外审计、公共预处理、进程和模型加载、场景/文件读取、保存均不计入上述规划时间。

## 配对比较与重复差异

对每个场景先用该方法三次成本的均值计算：

`收益 = 100 × (J_Detour − J_MLP) / J_Detour`。

- 平均配对收益：**0.2880%**。
- 95% 场景 percentile bootstrap 区间：**[0.0268%, 0.5818%]**；场景键排序后重采样 20,000 次，固定种子 731203。
- 场景胜 / 平 / 负：**12 / 2 / 4**。
- 总体规划中位数之比：**1.0064**；逐场景时间比的中位数：**1.0023**。两个统计量口径不同，不相互替代。

软预算的实际可完成调用数受到计时变化影响。Detour 的 18 个场景中有 **17 个**在三次运行间出现调用数变化，**10 个**出现最终成本变化；MLP 分别为 **15 个**与 **8 个**。最大场景内三次耗时极差分别为 **110.64 ms**与 **74.54 ms**。这些变化全部保留，没有挑选最优重复。

区间的重采样单位是 18 个场景，三次重复没有被当成 54 个独立场景；该区间条件于每场景三次测量的聚合值，不完整覆盖计时噪声，也不包含训练种子、不同硬件或其他场景分布的不确定性。区间下界距离零很近，应把结果解读为小幅、条件性的质量证据，不作为广泛稳定优越性的证明。

## 对原第四版结论的影响

原 Windows 同时间预算实验没有评测旧 MLP；本次补齐了这一缺口。在当前执行环境下，旧 MLP 使用略少的修复调用，仍得到小幅更低的平均成本，且总体实际中位耗时接近 Detour。这与其作为轻量候选的解释相容。

**原第四版“Structured 未达到采用门槛、默认保留 Fixed3 / Detour”的结论不变。** 本次没有重跑 Structured，也不能通过跨操作系统表格比较声称旧 MLP 已经在同时间下击败 Structured。本次结果适合新增一个单独的“冻结轻量模型同预算描述性补充”小节，并把旧 MLP列为可选择的质量模式候选；正式部署选择仍取决于用户需要的延迟边界和经验证的机器人操作空间。
