# 原M1停顿原因：已确认主机睡眠，未定位单文件延迟

Windows System事件日志提供了原尝试期间的直接主机证据，原始摘录保存在 `HOST_POWER_EVIDENCE.json`，没有修改原M1收据。

- Power-Troubleshooter事件1记录睡眠开始 `2026-11-11T04:45:51.449057300Z`，唤醒 `2026-11-11T05:33:13.772387200Z`，约2842.323秒。
- Kernel-Power事件42记录进入睡眠原因 `Application API`。事件本身没有指出调用的应用程序，不能猜测是某个用户动作或软件。
- Kernel-General事件1记录与硬件时钟同步导致系统时钟前移2,829,119毫秒；另有待机退出记录。故不能将外部等待工具的47分钟解释为已执行47分钟源码hash计算。

这段主机暂停覆盖了原累计2859.2566759秒中的绝大部分，是长时间无进展的已证实主要原因。原程序在恢复后才执行下一次合作式 `budget.check` 并检测超限。旧工具等待返回值不是独立的进程期限监督机制。

旧失败只保留汇总82次已插桩读取/hash（含登记阶段5次）、源码循环的检测栈，没有逐文件开始/结束和字节记录。因此具体文件的I/O延迟、磁盘或杀毒软件影响均为 **UNKNOWN**，不将其作为已证实原因。计数推导出的循环位置也不能替代真实逐文件时序。

本轮修复由独立监督进程控制工作进程和仅属于本实验的进程树；工作进程逐阶段、逐文件记录hash开始/结束、实际字节、耗时和最后完成操作，分块检查期限。主机睡眠可能暂停监督进程，因此监督必须同时记录实际墙钟并在恢复后保留任何超限，不能声称操作系统睡眠期间仍能实时执行终止命令。

**原2859.2566759秒和全部失败继续原字节保留，不扣除睡眠时间、不截断到1800秒。** 新恢复尝试是用户另行授权的独立一次1800秒尝试，与旧消费明确相连。
