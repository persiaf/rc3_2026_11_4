RC3 v5：冻结模型图嵌入缓存的维护边界

性质与接口

本适配器复用 rc3_v4/training/structured.npz。未训练网络，未改变检查点、
STOP 阈值、修复算子或旧版模型选择结论。它缓存固定图输入经过 graph_pool
后的向量，仅减少重复计算。主规划方法的采纳与该工程诊断相互独立。

使用方式：
    from rc3_v5.policy import load_policy
    policy = load_policy('rc3_v4/training/structured.npz')
    plan, info = rc3_v4.runtime.run(problem, 'learned', policy, 8)
    policy.invalidate()

接口支持冻结的 v4 NumPy .npz 检查点，不接受训练中的 PyTorch .pt 模型。
CachedGraphPolicy.model 是只读属性，权重用不可写 bytes 缓冲区承载，
权重映射与元数据冻结。普通数组写入、恢复 writeable 标志、替换权重映射、
修改 variant 等操作会报错。需要换权重或配置时必须重新 load_policy。
这些约束是普通调用者的 API 边界，不是防止恶意 Python 反射的安全沙箱。

缓存的键与动态信息

只有同一 Env 对象、相同完整 route 和相同有序 (start,end) 窗口布局可以命中。
新 Env（即使 problem 相同）、路线变化、窗口数量或顺序变化自动重新编码。
同一 Env 内的 problem/F/nav/nav costs/scene 对象替换会明确报错。
28 维动态统计、动作掩码、rank、gain、positive 及 STOP 池化每步重算；
不能缓存 logits 或最终动作。同路线上的剩余预算与掩码改变会改变输出。

F、D、候选/任务语义及地图必须在整个 Env 生命周期内静态不变。这也符合
rc3_v3.environment.Env 自己的路线与特征缓存前提。在线改变这些内容时，
需要重建 problem/Env；invalidate() 只清除本适配器缓存，不能使旧 Env 的
内部特征缓存适应新地图或新任务。适配器不在每个动作上重新哈希整个 F/D，
因此不承诺检测数组或嵌套 scene 字典的原位修改。不得将这项静态场景维护
宣称为已经支持动态任务到达或在线地图变化。

上传脚本的反例与改进依据

source_adapter_counterexamples.py 在独立内存模型中读入上传的审查适配器。
先填充缓存，再对其 graph_pool.bias 加 0.5，旧适配器仍命中旧图向量；
相对于相同修改后权重的完整前向，三个输出头的最大绝对差分别约为
5.4530163、0.0314897、3.4106293。新适配器对该写入抛出 ValueError。
原脚本已声明权重需固定，因此这是违反其输入契约后缺少防护的示例，
不是对原脚本在合法静态输入下计算正确性的否定。复现过程没有改写 NPZ。
完整数值与说明见 source_adapter_counterexamples.json。

正确性证据

test_cache.py 包含 11 项测试，覆盖同路线预算变化、掩码与 STOP 池化变化、
新 Env、新 problem、改路线、换窗口顺序、主动失效、不可变模型、空或非法
观察、替换静态数组、control 检查点及拒绝 .pt。

equivalence/ 是冻结的 18 个原验证场景，不是新测试集。每场景按原模型
完整运行 8 次决策，合计 144 个状态。三头张量用 np.array_equal 比较，
包含无穷掩码模式，并比较动作；全部逐位相同。另对每场景各运行原策略
与缓存策略一次，保存共 36 个完整计划，计划对象完全一致，均经独立
validator 检查。144 次决策和 36 个完整计划是不同证据分母，不能相加
称为 180 个测试场景。结果在 equivalence/summary.json 和 plans/ 中。

计时协议与可解释范围

cache_diagnostic.py 默认只跑正确性检查；必须显式 --profile 才启动计时。
每次结果必须写入新的空目录，避免悄悄覆盖历史证据。18 个冻结验证场景，
原版与缓存版各 3 次，即 108 个完整计划；每场景随机交错六次运行顺序。
固定 8 步，在计时前冻结场景、检查点 SHA、代码 SHA、顺序种子和协议。
同一 host/Python/NumPy 条件下比较，保留完整计划、原始重复值、各组件时间、
独立验证结果及中位数。使用墙钟完整规划时间，包含线程会话、Fixed3 初解、
策略特征、修复和最终验证；共同预处理、模型加载、额外复查和磁盘写入不计。
组件时间并非互斥分解，不应直接将各项相加与总时间比较。

计时脚本 profile 模式不会重复三头比较：head_checks=0，其相应 all(...)
布尔字段只表示该空集合没有失败，不能引用它们作为额外逐位证据。逐位证据
应明确引用 equivalence/ 的 144 次检查。profile 负责 108 个完整计划的
同一性、独立有效性与计时。

报告时区分每场景三次的中位数、18 个场景中位数的中位数、配对速度比中位数、
配对降幅中位数与两个总体中位数之比。这些聚合通常不相等。一次主机诊断
不能证明不同 CPU、BLAS、线程状态或负载下稳定加速；缓存命中比例也依赖
策略接受修复后路线是否改变。完整路线时间未必与单网络时间同比下降。
没有在新测试集上重做质量评估，不得据此推翻 v4 结构化模型未通过采纳门槛
的结论，也不能把外部 Linux 计时与本地 Windows 计时混合汇总。

本机诊断结果（只运行一次预声明的完整协议）

benchmark/ 保存 108 次完整计划，18 场景全部在原版/缓存版及各重复之间
计划对象相同、验证有效且目标不增。先取每场景三次中位数，再取18场景
中位数，完整规划为 486.590 → 441.871 ms；对应两总体中位数之比 1.1012。
场景配对速度比中位数为 1.0924，配对降幅中位数为 8.4528%，17 场景变快、
1 场景变慢。推理组件中位数为 75.449 → 36.356 ms。该主机上的整体降幅
不应写成网络推理的降幅，也不应宣称每个场景稳定加速。

verify_cache_artifacts.py 从保存的计划、场景和原始记录重新读取，重新独立
验证 equivalence 的 36 个计划和 benchmark 的 108 个计划，重数 144 条
逐位记录，核对 CSV 与原始 JSON，并重建上述统计；全部通过。结果见
artifact_reconstruction.json。复查不是新增场景或新增性能运行。
