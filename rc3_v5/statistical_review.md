## 公平性与时间口径

已确认的公平条件：两个方法使用完全相同的原保存场景和共同预处理，每次计时都重新构造并认证自己的 Fixed3 初解；同为 0.4 s 软预算、256 次修复上限；每景六次运行按固定种子随机交错。所有重复均保留，未挑最佳重复。完整规划计时包含初解、特征、策略推断、修复、最终验证以及模型线程会话开销。

冻结权重 SHA-256 为 `63e200f204b1e53c630f178bf7f60665944222becb60126b11c6461613db234d`。Linux 与 Windows 的实验脚本哈希均为 `7180e866fa6942b10ed306b17bcf4653afb02562243836c1dd544786222b6b85`，冻结源码、原场景及权重核对通过。此次未训练、未重新选模型、未调整 STOP 阈值。

以上是先在每景取中位数、再跨场景取中位数的结果。“逐景时间比的中位数”另为 Linux 1.002320、Windows 0.993316，不能与表中比值互换。实际中位耗时接近只是描述性观察；没有做延迟等价检验，不能称严格相同耗时。

这些数值不是冷启动总延迟。进程与模型加载、场景读取、共同导航／可达关系预处理、额外计时外审计和落盘均未计入；两方法在正式实验前经过一个 2×2 开发场景的预热。计时包含规划器自己的强制认证，额外审计是另一遍。若另报“含预处理总时间”，必须明确仍不含进程／模型冷启动，不能将不同场景分布的两个中位数直接相加冒充总时间中位数。

所有 108 次运行在每个平台均以 deadline 结束，均越过 400 ms，均未触发回退。已经启动的原子修复和最终认证允许越过截止点，所以“400 ms 预算”只表示启动新修复的软预算，不能保证在 400 ms 内返回。结果目标是 `J=底盘路程+0.75×停靠数`，不是含机械臂操作、升降和转向的实际任务总时间。

## 统计范围

Bootstrap 以 18 个场景为重采样单位，20,000 次、固定种子 731203；没有把每景三次重复当成三个独立场景。其区间条件于已经观测到的三次聚合结果，未完整包含计时噪声、训练随机性、硬件变化或新场景分布的不确定性。两个平台是分开的描述性复测，不是新的训练种子。

补评是在看到第四版结果后选择的模型／预算／规模组合，且未做多重比较调整。保留原测试集与原门槛、明确事后性质是正确做法；这不能自动把事后区间升级为预先登记的确认性证据。当前仅覆盖 regular、mixed、blocked 各六个百桌实例，不支持新复杂度或跨规模主张。

Windows manifest 的 `cpu_model` 为空、`cpu_quota` 为 null，记录了操作系统和 Python／NumPy／SciPy 版本，却未给出该时刻完整硬件／负载证明。这不影响同批随机交错的描述性比较，但限制跨机器性能解释。即使操作系统字符串相同，也不能宣称不同日期是完全相同硬件负载条件。
