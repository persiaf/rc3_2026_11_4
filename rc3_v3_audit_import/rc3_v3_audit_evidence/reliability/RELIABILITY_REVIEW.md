# v3 运行可靠性、缓存、预算与可复验性审查

本审查只读使用上传 v3 源码。没有改动算法、重新训练或生成 v4。结论区分本轮独立重跑结果与上传包已有记录。

## 1. 核心判断

v3 已形成可用于论文软件实验的方法闭环：三种构造候选先按抽象成本比较，验证胜出的 Fixed3 初解；学习模型只选择局部改进；确定性覆盖修复保持组合约束；最终完整路径独立验证失败时返回已验证初解。

这支持的可靠性命题是：**在当前离散候选、固定静态最短路矩阵和代理可达性模型下，只要建立了通过独立检查的 Fixed3 初解，所有成功返回的计划完整覆盖任务，并满足最终成本不高于该已验证 Fixed3 初解。** 它不要求神经网络预测一定正确。

当前并不支持硬实时、全局最优、真实机械臂 IK/轨迹可行、双臂同步操作或实机任务成功率等结论。学习是否有独立价值还须看同预算对照；可行性保底本身不是学习能力的证据。

## 3. 为什么缓存键在当前契约内足够

`environment.py:36–56` 每个服务位置采用步长 1，从最大宽度 4 递减寻找满足必要任务数不超过 8、候选数不超过 80 的窗口。

缓存签名在第 52 行包含：局部原始停靠序列及入口/出口、必要任务 ID、局部候选池 ID。必要任务和候选池会随窗口外覆盖关系变化而更新，因此修复了上一版“局部节点未变就永远屏蔽”的问题。`test_external_coverage_context_reopens_failure_without_clearing_cache` 已实际重跑通过。

同一 Env 内，可达矩阵 F、候选物理含义、导航距离矩阵 D、停靠罚项均保持固定；相同签名因此对应相同局部 DP 数据与原局部成本，无需在每个键里复制常量矩阵。只缓存确定性“无改进”结果，成功结果不缓存，异常或非法结果也不缓存。

这个性质以 problem 不在回合内改变为条件。它不自动适用于在线障碍变化、导航代价实时更新或可达性改变；这些情况下应建立新问题/新环境或明确使缓存失效。当前场景任务均在规划开始前给定。

教师标签缓存更保守，`data.py:TeacherLabels` 按完整路线和窗口索引缓存，每个问题单独持有，也不会把不同外部路线的标签混用。

## 4. 最终不劣于 Fixed3 的证明对应实际代码

`runtime.py:41–56` 先构造 recipe 0/1/7 路线，按抽象目标排序，依次尝试独立认证，取得已认证参照 A。正常无失败时就是三者中成本最小的 Fixed3。

`runtime.py:109–117` 对中间路线只检查完整覆盖、有限成本和相对前一步不增，明确标记 `independently_certified=False`。中间路线不能作为实机可执行认证结果。

`runtime.py:126–139` 仅将最后一个更好的候选完整展开并独立认证，确认导出成本等于抽象成本且不超过 A；通过才替换输出，否则保留 A。因此：

\[
J_{\mathrm{returned}}\le J_A,
\qquad \mathrm{valid}(\mathrm{returned})=\mathrm{true}.
\]

`_certify` 不只读取旧标志：它调用 `export_plan`，后者重新调用标准库独立验证器。验证器独立重算逐任务代理可达性、任务分配完整性/唯一性、用臂编号、导航访问顺序、膨胀障碍与折线碰撞、折线长度及成本。规划器用向量化几何和图导航，验证器用标量可达性和逐段碰撞算法。

没有获得任何已认证初解时，规划器明确返回失败，而不是声称保底成功。`fallback_used` 记录包括候选构造/模型/认证异常，不一定意味着最终输出必然回到了原始初解；应结合 failure stage 与 trace 解读。

最终认证失败时，返回 A 可能高于此前某个未认证中间路线的抽象成本，所以不应宣称“所有含回退事件的 trace 成本都永不回升”。真正保证是**最终交付不劣于已认证参照**。

## 5. STOP 与 wall-budget 的正确解释

最终 NPZ 元数据是 `gain_supervised`、`mlp`、`rc3-v3-budget28`，STOP 使用独立二元阈值 0.9。它比较 STOP logit 与 `log(0.9/0.1)`，不再让 STOP 和数量可变的窗口 logits 争一个 argmax。

STOP 表示**停止进一步优化**。初始 Fixed3 已覆盖全部任务，因此 STOP 不表示放弃剩余任务，也不是机器人的运动急停或任务执行终止。

`runtime.run` 的软截止时间从参照构造之前开始，包含参照构造/验证、特征、模型、修复及最终认证；它不包含 `Planner.plan` 在调用 runtime 之前做的地图/可达性预处理，不包括进程启动、模型加载和写盘。

代码在观察前、观察后和模型选完后检查截止时间，不会在已超时后主动开始下一次 DP。但是正在运行的一个 DP、生成合法初解所需工作以及最终强制验证都可能使实际返回时间超过预算。即便预算为零，仍先给出一个已验证参照。这一行为在本轮单测中实际检查。

论文应报告实际完整耗时与超时比例，不宜只列 200/400/800 ms 作为“保证响应时间”。固定 DP 调用数与固定软 wall-budget 是不同的比较协议。wall 模式 horizon=256 超出训练 horizon=8，且当前 wall 结果仅在百桌场景测过。

## 6. 当前输入和机器人约束的边界

规划接口检查：连续整数 ID、合法 table_id、有限任务点和停靠位姿、固定升降高度、至少有可达停靠及双向导航连通性。不可达与非法输入保留任务，不偷偷删任务凑完成率。

当前生成器满足每桌 0～3 个点任务、桌内采样和静态障碍。自定义 JSON 的接口检查并未验证任务一定在其声明的桌面矩形内、z 一定对应该桌高度，也没有任务工具姿态、抓取方式、持续时间、优先级或双臂同步约束。这不影响当前由生成器产生的实验，但说明实际桌面任务接口尚未完成。

模型仍是带肩偏置的球壳/扇形独立单臂可达性。左/右臂只是每个任务的可选执行者；任务按顺序服务，不含双臂同步、互碰和资源调度。h=0.40 为固定元数据，肩高 0.75 为独立常量，未建立升降高度到肩位姿的变换。

更关键的是，`prepare` 仍重算代理 F，独立验证器仍用 `proxy_reachable` 复算相同物理假设。因此“第一章真实工作空间已经接入”目前不能成立。接入真实离线 IK／工作空间证据时，应同时版本化规划可达接口和独立验证依据；只替换 F、保留旧球壳验证器会产生错误拒绝或错误解释。训练依然可以保持二维，只将真实操作空间限制作为离线输入。

## 7. 可收敛的研究主线与剩余小问题

从可靠性工程看，现阶段适合冻结这个算法结构与部署模型，把重心转向学习独立收益的统计解释、真实工作空间输入和有限实机验证，不需要为了继续迭代而新增一版网络。

存在两个复现工具层面的小问题，不影响本次匹配的实验结果：

1. `verify.py` 直接使用历史 Windows 路径和反斜杠形式 manifest 路径，在别的目录/系统上不能原样定位。此次审查以只读路径映射核查，提供的审查脚本支持 `--source-root`。
2. `verify.py` 收集了 source hash 匹配结果，但源码不匹配时没有把该项加入总 errors，因此将来可能出现源码变更而总 `all_passed` 仍为 true。本次独立确认所有源码哈希匹配，故现有记录不受该缺口影响；下一次正常维护时应让哈希不匹配直接使验证失败。
