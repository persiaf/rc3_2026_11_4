# 第三版实验独立复核与收敛建议

审计日期：2026-11-03。原上传目录保持不变。本目录按原始 `metrics.json`、每次运行记录、冻结哈希及工程计时原始记录重算；不复训网络，不重跑整套性能实验。最终计划的全量几何复验由另一项独立审计完成，本报告不重复宣称执行了该复验。

## 1. 当前判断

第三版已经把“较强初解、连续覆盖修复、最终独立认证”做成一个完整且有证据的规划流程。快速默认方法仍应选 **Fixed3**；需要额外质量时，**Fixed3 + Detour 规则引导修复**是当前更合理的实际入口。学习选择器保留为可选研究策略。其收益在部分规模和较小修复预算下存在，但尚不足以成为通用默认方法。

这不是要求再做一版 PPO 调参。第二版提出的 Fixed3 初解、更合理的邻域、预算状态、终验调度、多状态监督等已经落实。第三版最有价值的下一步，是把当前工程主线接到可信机械臂可达关系，并明确质量/时间约束；继续把桌数扩大到更多压力规模并不能弥补这些证据缺口。

## 3. 必须分规模报告速度与质量

以下使用最多 8 次 DP 修复。每格为“相对同场景 Fixed3 平均降本 / 完整规划中位数”。完整规划包含初解、特征、模型、修复、必要最终验证，**不含共享场景预处理、进程启动、模型加载和写盘**。成本为路程加 0.75 倍停靠数。

| 桌数（场景数） | Fixed3 规划 | Detour 降本 / 规划 | Learned 降本 / 规划 |
|---|---:|---:|---:|
| 12（9） | 2.90 ms | 0.699% / 12.45 ms | 0.699% / 19.02 ms |
| 36（9） | 10.39 ms | 0.963% / 43.74 ms | 1.029% / 65.32 ms |
| 64（9） | 33.55 ms | 0.721% / 97.74 ms | 0.822% / 123.96 ms |
| 100（9） | 68.52 ms | 0.914% / 201.15 ms | 0.670% / 210.19 ms |
| 144（9） | 138.23 ms | 0.464% / 362.07 ms | 0.963% / 373.82 ms |
| 196（9） | 295.75 ms | 0.602% / 777.11 ms | 0.536% / 775.92 ms |
| 256（3，压力） | 531.80 ms | 0.088% / 957.49 ms | 0.257% / 1,154.24 ms |
| 400（3，压力） | 1,939.49 ms | 0.386% / 3,627.06 ms | 0.236% / 3,350.90 ms |

因此不能用“54 个混合规模主场景 Learned 中位 177.39 ms”描述百桌性能。对应百桌值是 210.19 ms；若首次建立场景预处理，百桌 Learned 冷总中位是 377.93 ms，Fixed3 为 248.69 ms。

400 桌 Learned 的三场景规划中位依次为 3.351、1.954、4.052 s，加入各自共享预处理后为 5.818、5.121、7.045 s；**跨这 3 场景的冷总中位是 5.818 s**。它是“各场景 3 次规划时间中位 + 同场景预处理”再取跨场景中位，不能把不同分量的总体中位数直接相加。规模可运行性已经测到 400 桌，但当前不是该规模的毫秒级规划证据。

原始与逐场景时间分解见 `focused_100_400_raw_runs.csv`、`focused_100_400_scene_medians.csv`；全规模数据见 `group_statistics.csv`。

## 4. 学习的独立贡献：有局部信号，没有稳定全面优势

本次以场景为配对单位，20,000 次 bootstrap，seed 20261103。重复壁钟成本先在同场景内求均值。相同数据的分组别名使用相同抽样，避免同一组结果出现不同区间而被选择性引用。

| 比较 | 场景数 | 学习相对对照成本下降 | 本次 95% 区间 |
|---|---:|---:|---|
| 主场景，8 次，vs Fixed3 | 54 | 0.78645% | [0.50720%, 1.14437%] |
| 主场景，8 次，vs Detour | 54 | 0.06015% | [-0.11133%, 0.23603%] |
| 主场景，8 次，vs Random | 54 | 0.14598% | [-0.00080%, 0.27672%] |
| 百桌，8 次，vs Detour | 9 | -0.24902% | [-0.77246%, 0.30800%] |
| 144/196 桌，1 次，vs Detour | 18 | 0.20873% | [0.08909%, 0.34146%] |
| 144/196 桌，2 次，vs Detour | 18 | 0.28654% | [0.12317%, 0.47646%] |
| 144/196 桌，4 次，vs Detour | 18 | 0.26422% | [0.05221%, 0.52432%] |
| 144/196 桌，8 次，vs Detour | 18 | 0.21639% | [-0.06311%, 0.52312%] |
| 压力，8 次，vs Detour | 6 | 0.00812% | [-0.36431%, 0.35046%] |
| 百桌，400 ms 档，vs Detour | 9 | -0.32212% | [-0.64156%, -0.02182%] |
| 百桌，800 ms 档，vs Detour | 9 | -0.26545% | [-0.53364%, 0.00000%] |

报告原 5,000 次抽样中“主 54 例 vs Random”区间为 [0.003%, 0.275%]，本次预定 20,000 次复算下界略低于零。均值完全一致，这说明跨零判定对有限 bootstrap 抽样敏感，应表述为**边缘、脆弱的收益信号**，不能靠挑区间声称稳定显著优越。本次没有继续更换种子或反复抽样以获得有利结论。

144/196 桌的小调用预算有正收益信号，但它们也是多个规模×预算比较中的分组发现，未作多重比较修正，并且当前只测试了验证选中的一个检查点。既不能忽略，也不能扩大成“任意规模学习优越性”。可以将它写成后续独立验证的窄假设；本批测试不能再用于挑选并宣称该窄区间是预设应用范围。

一个新而具体的效率诊断是：12 桌 Learned 与 Detour 的最终成本相同，学习平均仅调用 2.78 次，规则约 7.89 次，但完整规划仍为 19.02 ms 对 12.45 ms。因此 STOP 在这一批数据中确实省了修复次数，**还没有转化为更短的完整规划时间**。用“减少 DP 调用”代替“缩短时间”会夸大应用价值。

## 5. 软时间档的边界和可操作改进

百桌壁钟的分母为 9 个场景，每配置 27 次实际运行。时间档是搜索停止控制，不是完整端到端硬时限。

| Learned 时间档 | 场景中位的总体中位 | 超时运行 / 27 | 最大完整规划 | 最大超时 |
|---|---:|---:|---:|---:|
| 200 ms | 228.92 ms | 27 / 27 | 257.05 ms | 57.05 ms |
| 400 ms | 428.02 ms | 27 / 27 | 454.94 ms | 54.94 ms |
| 800 ms | 824.09 ms | 21 / 27 | 853.33 ms | 53.33 ms |

`runtime.run` 在新修复启动前检查时钟，当前 DP 和最终几何验证不可中断，因此上述超时与源码语义一致，不是漏记时间。共享导航预处理尚在该时限外，不能把 200 ms 档描述为首次场景到完整方案 200 ms。

当前实际时间竞争也暴露出方法代价：400 ms 档 Detour 平均完成 36.70 次修复，Learned 为 26.26 次；最终规则成本更低。这里的收益差既含排序质量，也含额外推理开销，两者都属于实际部署效果。

另一个需要正视的建模差异：网络预算特征来自 `steps / horizon` 和剩余调用比例；壁钟模式令 horizon=256，训练最大 8 步。网络没有输入真实剩余壁钟时间，故这不是经过时间约束训练的策略。若以后单独研究软时间效率，应把预估修复/认证时间、实际时间余量和搜索收益一起建模，并在新数据上验证；本轮不宜继续把调用预算外推结果当作时间适应能力。

若实际任务要求明确时限，先标定并为最终认证预留时间；必要时在满足时限时直接返回已验证 Fixed3。预留统计分位数只能降低超时概率，仍不等于硬实时最坏情况保证。当前研究无需为了证明硬实时而扩大范围，应先明确机器人任务允许的规划时长。

## 6. 工程提速是真实的，但不属于学习贡献

从 `engineering_profile_runs.csv` 与 `engineering_profile.json` 的原始 108 次记录独立重算：

- 18 个冻结验证场景，两个实现各 3 次，随机交错顺序。
- 逐场景所有输出成本一致；原代码在计时外额外复验，记录均通过。
- 每次自身重构三配方候选，共享只有 `Problem` 预处理，没有免费复用路线或参考计划。
- 旧/新完整规划总体中位 **141.559 / 77.3569 ms**。
- 逐场景速度比中位 **1.80220 倍**；两个总体中位数之比是另一个量 **1.82995 倍**。
- 18/18 场景新实现更快，逐场景耗时下降比例中位 44.51%。
- 加相同预处理的冷总中位 **334.227 / 268.606 ms**。

源码证明必要内部认证已计时，额外外部复验计时外；这对两边一致。新流程按代价排序候选，只对最优可认证候选执行完整导出认证；旧流程对三个候选逐一完整认证。任务、目标与返回合法性一致，认证调度不同，正是本次工程优化的对象。

这个独立验证集诊断可以写成工程贡献，不能挪作“学习模型快 1.8 倍”，也不能并入 60 个冻结测试场景的样本数。见 `engineering_summary.json`、`engineering_pairs_recomputed.csv`。

## 7. 一个可小范围修正的推理开销

百桌 8 次 Learned 的模型部分总体中位为 23.84 ms，特征约 28.74 ms、修复约 52.24 ms、最终认证约 26.06 ms、参考构造及认证约 70.19 ms。各分量中位不是同一次运行，不能直接相加。

`model.py` 的 NumPy 推理每次 `outputs()` 都构建 `threadpool_limits` 上下文，会重复枚举已加载线程库。一个真实百桌验证状态（76 窗口、28 特征）的本机微测，在外层统一单线程 BLAS 控制下，只去除内层重复控制，所有数值输出完全相同：每次调用从 0.3974 ms 降到 0.1131 ms。各条件 5 个随机顺序块，每块 200 次。它确认了这项可去除开销；并不说明原 Windows 每步约 3 ms 都来自这里，也不能据此声称完整规划同倍提速。

可在模型进程或规划调用外层统一管理线程，避免每个动作重复扫描；对所有比较方法一致设置，并验证输出一致。该优化足够小，不需要重新训练或改数学模型。微测脚本与结果：`profile_policy_context.py`、`policy_threadpool_microprofile.json`。原上传源码未改。

## 8. 下一步应该收敛到什么

### 实际入口

1. **快速模式：Fixed3。**提供完整路线、任务服务顺序、独立验证和明确失败记录；可在静态场景重复使用时缓存导航图/候选间距离，但必须用地图、候选位姿、底盘尺寸等完整键失效，并实测冷热两条路径。
2. **质量模式：Fixed3 + 有限预算 Detour 覆盖修复。**现有百桌 1/2/4/8 调用档对应约 0.207/0.428/0.593/0.914% 降本、108/123/133/201 ms 规划。它提供可解释的质量/时间选项，不能把其中一个档事后选出又称其为未见测试上的预设最优档。
3. **学习模式：保留可选，不继续强行做主入口。**应明确其优势假设是“在一定场景和预算下更有效地选择修复”，而不是“天然快于规则或保证可行”。可行性与成本上界本来由验证结构提供。

### 研究主线

优先把第一部分真实工作空间、姿态、升降、双臂服务条件变成离线可达/服务配置接口，然后交给同一个二维高层规划器。这个连接比把压力场景从 400 桌扩大到 600 桌更直接补足论文的机器人属性。训练仍可二维，不必把机械臂关节运动逐步加入学习。

进一步质量证据应来自：小问题的最优差距、比当前局部规则更强的联合覆盖/路线对照，以及同一物理约束下的统一质量/时间曲线。学习不是第三部分必须保留的结论。如果继续研究学习，应先明确独立收益的最小有用幅度与时间容许量，再用新冻结数据检验；不能只追加训练轮数直到本次 60 例变好。

当前阶段可以收敛为“受可达约束的快速覆盖路线规划及有成本保障的预算修复”，将学习作为可检验的扩展。已经完成的可靠初解、延迟终验和故障回退应作为明确的方法性质；尚未证明的实机可达性、全局质量和学习普适优势保持独立，不互相替代。
