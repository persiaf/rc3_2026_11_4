# 第二版局部修复与可靠性核查

## 结论

当前固定入口/出口覆盖修复的 DP 与宣称的受限问题一致，已验证初解和独立验证保底实现成立。此次独立重跑 `test_repair`、`test_reliability` 共 16 项测试全部通过。未发现需要否定已生成方案可行性或成本不增性质的实现错误。保证只针对当前离散候选、静态通道图、独立单臂可达性代理；不能外推为真实双臂同步操作、升降动作或实机成功率。

新做 8 个百桌开发场景诊断，初始种子为 4200000200～4200000207，与上传的训练/验证/测试种子均不重叠。48 个最终方案均经过原独立验证器检查并通过。这是**探索性的邻域与教师潜力诊断**，不是另一次冻结测试，也没有运行 BC/PPO。不能把以下结果写成“新学习模型已超越基线”。

## 1. 精确性与保底的条件

`repair.py:70–88` 定义要修复的任务集为删除片段之后失去全部覆盖的任务。其余任务仍由保留停靠覆盖。候选池包含覆盖这些任务的全部可导航候选，明确保留原片段的候选，并排除已在其余路线出现的候选。

`repair.py:134–199` 用状态 `(已覆盖任务位掩码, 最后停靠)` 动态规划。每次转移至少增加一个必要任务的覆盖。当前图使用非负最短路距离、停靠罚项非负，因此任一不增加覆盖的中间停靠均可由最短路直接连接取代，成本不会上升。无需额外记录访问集合：某候选第一次访问已加入其全部覆盖，之后不可能再次带来新的覆盖。因此该 DP 在声明的局部候选集、固定端点、无额外容量/先后顺序/同步双臂约束的条件下精确。

原片段是可恢复的可行选项；即使数值异常、超限或找不到更好路线，也返回原路线。默认只在必要任务数不超过 8、候选数不超过 80 时使用 DP。

`environment.py:45–47` 将超限窗口直接屏蔽，默认策略不会浪费一次动作在这些窗口；`repair_window` 内的超限返回原解是第二层保护。`evaluate.py:35–96` 在初解及每次实际改变路线后导出完整路径并独立验证，再用导出后的完整目标比较，只接受成本下降。异常会保留已验证 incumbent。由此能证明的是输出相对该次已验证 Fixed1 初解不劣；不是相对全局最优的近似比，也不是硬实时保证。

## 2. 当前搜索空间是否已经没有余量

在每个 fresh 场景，分别由 Fixed1 和 Fixed3 最好初解出发，最多执行 8 次修复。随机和 detour 每步只调用选中的局部修复。`best_immediate` 每一步先穷举当前所有可选窗口，再选择即时收益最大的一个；它使用与原方案相同的 DP、默认宽 3/步长 2 窗口及历史掩码。

它是昂贵的**逐步贪心参考选择器**。穷举了本步窗口，不代表求出了所有 8 步序列的最优值，更不是全局路径最优值或数学上界。其价值是回答“在现有邻域里，一个准确的窗口选择器是否还有东西可以学”。

| 初解 | 选择器 | 相对自身初解平均成本下降 | 相对 Fixed3 平均成本下降 | 搜索循环中位数 |
|---|---|---:|---:|---:|
| Fixed1 | random | 0.1365% | -1.0281% | 0.1239 s |
| Fixed1 | detour | 0.7348% | -0.4241% | 0.1546 s |
| Fixed1 | best_immediate | 1.4492% | 0.2929% | 2.7269 s |
| Fixed3 | random | 0.3434% | 0.3434% | 0.1304 s |
| Fixed3 | detour | 0.8310% | 0.8310% | 0.1621 s |
| Fixed3 | best_immediate | 2.1825% | 2.1825% | 3.1816 s |

上述时间只包含诊断搜索循环，排除了共享预处理、初解构造、最终导出及验证，不能与上传报告的完整规划时间直接比较，也不构成同时间预算对比。best_immediate 平均每例评估约 248/277 个窗口修复，远多于其他策略的 8 个。它应优先用于离线教师标签与训练状态收集。

Fixed3+best_immediate 对 Fixed3 为 7 胜、1 平、0 负；Fixed1+best_immediate 对 Fixed3 为 5 胜、1 平、2 负。后者说明：在当前邻域和 8 次预算下，只改善 Fixed1 的路线，连准确的即时选择器也不能保证击败另一个构造盆地中的 Fixed3 路线。**更强的验证初解与好的局部选择器是互补关系。**

这 8 个场景只能提供方向性证据。不要以此替代 108 个冻结测试、训练种子不确定性或同完整时间预算比较。

## 3. 主要限制来自哪里

默认 Fixed1 初解共 340 个窗口，335 个可修复，43 个有正收益；5 个因 9 个必要任务被屏蔽，0 个触发 80 候选限制，最大候选池只有 24。Fixed3 初解同样共 340 个窗口，333 个可修复，41 个正收益，7 个任务超限，0 个候选超限。

这批诊断不支持“候选上限 80 太小”作为主要原因。默认任务上限导致约 1.5%～2.1% 初始窗口被屏蔽，也不足以解释大部分表现差距。

把宽 3 窗口步长由 2 改为 1，Fixed1 初解窗口由 340 增为 667，正收益窗口由 43 增为 83；每例最佳单步收益均值由 1.6874 等效米增为 1.9838 等效米，8 例均出现可改善窗口。Fixed3 对应最佳收益从 1.9432 增为 2.1896。说明步长 2 确实遗漏部分有效局部变换，但完整枚举的开销也会上升。

直接把窗口宽度变成 4，在固定 task cap=8 下，Fixed1 有 70/335（20.9%）窗口超限，Fixed3 为 82/336（24.4%）。因此不宜只扩大窗口而保持所有其它设置。更稳妥的是用必要任务数约束生成可修复窗口，结合宽 2/3/4 和不同对齐方式，再由廉价筛选或学习排序控制 DP 数量。

所有这些仅衡量初始状态。正收益窗口会相互重叠，不能把其收益求和当作可实现的总改善。

## 4. 两个应明确的细节

### 历史窗口掩码没有编码外部覆盖状态

`environment.py:43,45,56` 用窗口内节点与两端点的元组记忆是否尝试过。然而 `_local` 的必要任务由整条路线的保留覆盖决定。外部停靠变更后，完全相同的局部节点序列可能对应不同的必要任务与新收益，旧签名仍会屏蔽它。这是保守的搜索限制，不破坏可行性保证。可考虑把局部必要任务集合/相关覆盖计数加入缓存键，或只在原路线版本内缓存“无改进”判断。是否值得修改，应测新增收益相对重新计算的代价。

### 固定端点局部收益上界不能直接包住全动作收益

可构造局部上界

`old_local_cost - D(entry,exit) - lambda * ceil(required_tasks / max_tasks_covered_by_one_candidate)`。

它对局部 DP 的改进是安全上界，但 `environment.py:59` 随后调用 `canonical_route`，可能删除窗口之外因新覆盖而冗余的停靠。整个动作的最终收益可能超过上述局部界。若用于优先队列排序无妨；若以它做精确剪枝，则必须把窗口外删除的可能收益也纳入安全界。

## 5. 下一轮最小有效改进

1. 保留 Fixed1 快速模式，建立 Fixed3 已验证初解的改善模式，使改善模型直接在强基线提供的路线空间里工作。新模型需在同类初解上训练；直接换初解属于分布变化，不能承诺现有权重效果不变。
2. 先以多步 best_immediate 轨迹收集监督数据。覆盖初解、中间改进状态及无收益状态，学习有效窗口/收益或收益与代价的排序；这比重复相同初始状态标签更贴近部署分布。
3. 报告“前 k 个被选窗口捕获的参考收益”、有收益窗口召回率及单位 DP 调用收益，区分分类/排序不准和邻域本身无潜力。不要只看训练损失。
4. 在同样完整规划时间或实际 DP 调用预算下，与 detour、random、Fixed3、Fixed3+detour 对照，再决定 PPO 是否值得继续。
5. 学习前后都保留独立验证。完整路径展开/验证可以做共享、缓存和阶段化，但必须保证最终交付仍通过同一标准；不能删除检查来制造加速。

运行层面的一个小问题：`plan.py` 的 `--method bc` 若不显式指定 BC checkpoint，仍使用默认 `deployment_v2/policy.pt`；该默认文件是选出的 PPO 模型。应在 CLI 中校验阶段或提供阶段对应默认路径，避免用户把同一个模型误当成两种方法。冻结测试明确加载了两个不同权重，不受这个 CLI 易用性问题影响。
